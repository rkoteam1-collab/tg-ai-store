# Перенос API и заказов в РФ

Этот комплект запускает **один** экземпляр Express и Telegram-бота на облачной виртуальной машине с подтверждённым размещением в РФ. GitHub Pages остаётся статическим фронтендом. Перенос кода сам по себе не доказывает выполнение 152-ФЗ, 54-ФЗ или регистрацию уведомления РКН.

## Перед запуском

1. Получить облачный сервер с подтверждённым регионом РФ, постоянным диском, публичным IPv4, доступом по SSH и доменом. Нужны Docker Engine и Compose plugin. Не размещать базу на зарубежном managed-диске или в зарубежных бэкапах. Проверить договор-поручение с провайдером: например, Selectel подтверждает соответствие своей **облачной платформы**, но прямо пишет, что его дешёвая линейка **VDS** не соответствует 152-ФЗ ([облачные серверы](https://docs.selectel.ru/cloud-servers/about/152-fz-cloud-server/), [VDS FAQ](https://selectel.ru/services/cloud/vps-vds/)). Не выбирать тариф лишь по месту размещения или цене.
2. Создать DNS A-запись домена на облачную машину; открыть входящие 80/443, SSH ограничить ключом и по возможности своим IP.
3. Убедиться, что на прежнем Render **заказов 0 и продажа выключена**. Если заказы появились, остановить миграцию: обычный админский список скрывает токены доступа, и его недостаточно для полного переноса.
4. На рабочем компьютере получить снимок каталога и промокодов: задать `MIGRATION_SOURCE_URL=https://tg-ai-store.onrender.com`, `MIGRATION_ADMIN_PIN` и новый путь `MIGRATION_OUTPUT_DIR` вне Git, затем выполнить `node scripts/export-live-state.mjs`. Снимок содержит текущие цены и промокоды; не публиковать его.
5. Передать снимок на облачную машину по SSH/SCP. Скопировать `.env.production.example` в `.env.production` **только на сервере**, заполнить секреты, выставить права `chmod 600`. Нужны новые длинные значения ADMIN_PIN; BOT_TOKEN и платёжные ключи хранить только в этом файле/секретном хранилище.

## Первый запуск

На сервере в каталоге `deploy/ru`:

```sh
docker compose --env-file .env.production build
docker compose --env-file .env.production run --rm --no-deps \
  -e MIGRATION_INPUT_DIR=/migration \
  -v /absolute/path/to/snapshot:/migration:ro \
  app node scripts/import-live-state.mjs
docker compose --env-file .env.production up -d
docker compose --env-file .env.production ps
curl -fsS https://shop.example.ru/api/health
```

Импорт работает лишь в **пустой** том и лишь при подтверждённых нулевых заказах. Не повторять импорт поверх живой базы. Тестировать админку через Telegram: на новом сервере включено `ADMIN_REQUIRE_TELEGRAM=true`, так что нужны и подтверждённый аккаунт владельца, и PIN.

## Переключение трафика

1. До включения продаж проверить домен/TLS, каталог, вход администратора. В админке создать тестовую карточку, изменить её цену и наличие, перезапустить контейнер и убедиться, что все три изменения сохранились. Затем удалить тестовую карточку и проверить удаление после ещё одного перезапуска. Сравнить реальные товары и промокоды с экспортом.
2. Установить GitHub Actions repository variable `BACKEND_URL` в HTTPS-адрес нового API и пересобрать Pages: обе ссылки на API генерируются из неё. Бот на новом сервере установит webhook на `BACKEND_URL`; проверить `getWebhookInfo` без публикации токена.
3. На Render отключить старого бота, старый API и старые платёжные ключи **после** проверки нового адреса; не оставлять второй работающий обработчик платежей. Старые ссылки на Render должны вести на новый адрес или быть выключены, чтобы покупатель не создал заказ в зарубежной базе.
4. Проверить у IT-Pay настройки webhook: `https://<новый домен>/api/payments/alfa/webhook`. Обновить их в кабинете, затем проверить подписанный платёж и статус заказа. Если провайдер требует отдельную настройку URL для каждого магазина, выполнить её там.
5. `PAYMENTS_ENABLED=false` в примере удерживает **новый** сервер от выставления счетов, пока не подтверждена ККТ. После регистрации/проверки кассы и настроек `ITPAY_*` сделать тестовую оплату, проверить настоящий фискальный чек с ФН/ФД/ФП и его получение клиентом, затем установить `PAYMENTS_ENABLED=true` и перезапустить контейнер. Платёжный код не удаляется.
6. После миграции исправить опубликованную политику: убрать описание Render Oregon, вписать фактического российского хостера, срок хранения и порядок трансграничной передачи. Не публиковать это как уже выполненный шаг до проверки хостинга.

## Резервирование

Ежедневно выполнять `docker compose --env-file .env.production exec -T app node scripts/backup-data.mjs` и проверять контрольные суммы/восстановление на отдельном тестовом экземпляре. Тома Docker переживают обычный перезапуск и пересборку контейнера, но их удаление или отказ диска уничтожит данные. Копии в томе `backups` находятся на том же сервере: дополнительно нужен зашифрованный бэкап **в РФ**, отдельно от основного диска. Не выгружать открытые заказы в GitHub, Render или публичное облако.

## Что подтверждается вне кода

- Уведомление об обработке данных в РКН, а при необходимости — о трансграничной передаче; проверить реальные договоры с Telegram и платёжным провайдером.
- Публичный адрес для претензий и сведения ИП.
- Регистрация ККТ/ОФД и реальные чеки. Отправка параметра `client_receipt` не означает, что чек создан.
- Основание для обработки, сроки хранения и процедура обработки запросов субъектов данных.
